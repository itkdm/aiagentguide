# 子代理驱动开发

通过为每个任务派发一个新的实现者子代理、在每个任务后进行任务审查（规格合规 + 代码质量），并在最后进行全分支广泛审查，来执行实现计划。

**为什么用子代理：** 你将任务委托给具有隔离上下文的专业代理。通过精确构造它们的指令和上下文，你确保它们保持专注并成功完成任务。它们绝不应继承你会话的上下文或历史——你精确构造它们需要的东西。这也保留了你自己的上下文用于协调工作。

**核心原则：** 每个任务一个新子代理 + 任务审查（规格 + 质量）+ 广泛最终审查 = 高质量、快速迭代！

**叙述：** 在工具调用之间，最多叙述一行短句——分类账和工具结果承载记录。

**连续执行：** 不要在任务之间暂停来与你的伙伴检查。执行计划中的所有任务，不要停止。唯一需要停止的理由是：你无法解决的 BLOCKED 状态、真正阻碍进展的歧义，或所有任务已完成。"我应该继续吗？"的提示和进度摘要浪费他们的时间——他们让你执行计划，所以执行它。

## 飞行前计划审查

在派发任务 1 之前，扫描计划一次，检查冲突：

- 任务之间互相矛盾或与计划的全局约束矛盾
- 计划明确要求审查标准视为缺陷的任何内容（一个不断言任何东西的测试、逻辑块的逐字重复）

将你发现的每件事作为一批问题呈现给你的伙伴——每个发现旁边附上要求其的原文，询问哪个为准——在执行开始前，而不是在计划中途每次发现一次就打断。如果扫描干净，无需评论直接继续。审查循环仍然是冲突的网，这些冲突只有从实现中才会出现。

## 模型选择

使用能处理每个角色的最弱模型，以节省成本并提高效率。

**机械实现任务**（隔离函数、清晰规格、1-2 个文件）：使用快速、便宜的模型。当计划被充分指定后，大多数实现任务都是机械性的。

**集成和判断任务**（多文件协调、模式匹配、调试）：使用标准模型。

**架构和设计任务**：使用可用的最强模型。最终的全分支审查也是其中之一——在可用的最强模型上派发它，而不是会话默认值。

**审查任务**：根据判断选择模型，根据 diff 的大小、复杂性和风险缩放。一个小的机械 diff 不需要最强模型；一个微妙的并发变更需要。

**派发子代理时始终明确指定模型。** 省略的模型会继承你会话的模型——通常是最强且最贵的——这会静默地破坏本节。

**轮次计数胜过 token 价格。** 挂钟时间和上下文成本随着子代理需要的轮次而缩放，而最便宜的模型在多步骤工作上通常需要 2-3 倍的轮次——总体上花费更多。将中档模型作为审查者和从散文描述工作的实现者的最低档。当任务计划文本包含要编写的全部代码时，实现就是转写加测试：对该实现者使用最便宜的档位。单文件机械修复也使用最便宜的档位。

**任务复杂性信号（实现任务）：**
- 触及 1-2 个文件且有完整规格 → 便宜模型
- 触及多个文件且有集成问题 → 标准模型
- 需要设计判断或广泛的代码库理解 → 最强模型

## 处理实现者状态

实现者子代理报告四种状态之一。适当地处理每一种：

**DONE：** 生成审查包（`scripts/review-package BASE HEAD`，从这个 skill 的目录运行——它打印写入的唯一文件路径；BASE 是你派发实现者之前记录的提交——永远不要用 `HEAD~1`，它会静默丢弃多提交任务的除最后一个之外的所有提交），然后派发任务审查员，传入打印的路径。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前读取疑虑。如果疑虑是关于正确性或范围的，在审查之前解决它们。如果它们是观察（例如"这个文件变得很大"），记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新派发。

**BLOCKED：** 实现者无法完成任务。评估阻塞：

1. 如果是上下文问题，提供更多上下文并用相同模型重新派发
2. 如果任务需要更多推理，用更强的模型重新派发
3. 如果任务太大，将其分解为更小的片
4. 如果计划本身有误，上报给人类

**永远**不要忽略升级，也不要在没有更改的情况下强制相同模型重试。如果实现者说它卡住了，说明有些东西需要更改。

## 处理审查员 ⚠️ 项

任务审查员可能报告"⚠️ 无法从 diff 验证"项——存在于未更改代码中的需求，或跨任务的。这些不会阻塞审查的其余部分，但你必须在标记任务完成之前自己解决每一项：你持有审查员缺乏的计划和下跨任务上下文。如果你确认某项是真正的缺口，将其视为规格审查失败——把它发回给实现者并重新审查。

## 构造审查员提示

逐任务审查是有任务范围的关卡。广泛审查只进行一次，在最终的全分支审查。当你填写审查员模板时：

- 不要添加开放式指令，如"检查所有用法"或"如果有用则运行竞态测试"，而没有具体的、特定于任务的理由
- 不要要求审查员重新运行实现者已经在相同代码上运行过的测试——实现者的报告承载测试证据
- 不要为审查员预判发现——永远不要指示审查员忽略或不标记特定问题。如果你认为某个发现会是误报，让审查员提出它并在审查循环中裁决。如果你正在编写的提示包含"不要标记"、"不要将 X 视为缺陷"、"最多 Minor"或"计划选择了"——停下来：你在预判，通常是为了省掉一个审查循环。
- 你交给审查员的全局约束块是它的关注镜头。从计划的全局约束节或规格中逐字复制绑定要求：精确值、精确格式，以及组件之间的陈述关系（"与 X 相同布局"、"匹配 Y"）。审查员模板已经携带了过程规则（YAGNI、测试卫生、审查方法）——约束块用于这个项目的规格要求。
- 将审查员的 diff 作为文件交给它：运行这个 skill 的 `scripts/review-package BASE HEAD` 并将它打印的文件路径传给审查员（或者，在没有 bash 的情况下：`git log --oneline`、`git diff --stat` 和 `git diff -U10` 用于范围，重定向到一个唯一命名的文件）。输出永远不会进入你自己的上下文，审查员在一次 Read 调用中看到提交列表、统计摘要和带上下文的完整 diff。使用你在派发实现者之前记录的 BASE——永远不要用 `HEAD~1`，它会静默截断多提交任务。
- 派发提示描述一个任务，而不是会话的历史。不要将积累的先前任务摘要（"任务 1-3 后的状态"）粘贴到后来的派发中——真正的会话派发达到 42k 字符，其中 99% 是粘贴的历史。一个新的子代理需要它的任务、它触及的接口，以及全局约束。没有别的。
- 为 Critical 和 Important 发现派发修复子代理。在进度分类账中记录 Minor 发现，并在最终的全分支审查中指向该列表，以便它可以分流哪些必须在合并之前修复。没有人读的汇总表是静默丢弃。
- 标记为 plan-mandated 的发现——或任何与计划文本要求矛盾的发现——是人类的决定，就像任何计划矛盾一样：呈现发现和计划文本，询问哪个为准。不要因为计划要求它而驳回发现，也不要在询问之前派发与计划矛盾的修复。
- 最终的全分支审查也获得一个包：运行 `scripts/review-package MERGE_BASE HEAD`（MERGE_BASE = 分支开始的提交，例如 `git merge-base main HEAD`）并在最终审查派发中包含打印的路径，以便最终审查员在一次读取中看到完整 diff 而不是用 git 命令重新推导分支 diff。
- 每个修复派发都携带实现者合同：修复子代理重新运行覆盖其变更的测试并报告结果。在派发中命名覆盖测试文件——单行修复不需要整个套件。在重新派发审查员之前，确认修复报告包含覆盖测试、运行的命令和输出；一旦三者都存在，再派发重新审查。
- 如果最终的全分支审查返回发现，派发一个修复子代理并附上完整的发现列表——而不是每个发现一个修复器。每个发现的修复器各自重建上下文并重新运行套件；一个真实会话的最终审查修复波的成本超过其所有任务的总和。

## 文件交接

你粘贴到派发提示中的一切——以及子代理打印回来的任何东西——在会话的其余部分中常驻于你的上下文中，并在以后的每一轮中重新读取。将工件作为文件交接：

- **任务简报：** 在派发实现者之前，运行这个 skill 的 `scripts/task-brief PLAN_FILE N`——它将任务的完整文本提取到一个唯一命名的文件并打印路径。构造派发，使简报保持唯一的需求来源。你的派发应包含：（1）一行关于这个任务适合项目哪个位置的内容；（2）简报路径，介绍为"先读这个——它是你的需求，包含要逐字使用的精确值"；（3）简报无法知道的来自先前任务的接口和决策；（4）你对简报中注意到的任何歧义的解决方案；（5）报告文件路径和报告合同。精确值（数字、魔法字符串、签名、测试用例）只出现在简报中。
- **报告文件：** 在实现者的报告文件之后命名（简报 `…/task-N-brief.md` → 报告 `…/task-N-report.md`）并将其放入派发提示中。实现者将完整报告写入那里，并只返回状态、提交、一行测试摘要和疑虑。
- **审查员输入：** 任务审查员获得三个路径——相同的简报文件、报告文件和审查包——加上绑定任务的全局约束。

## 持久进度

对话记忆不会在压缩后存活。在真实会话中，丢失位置的控制器重新派发了整个已完成的任务序列——这是观察到的最昂贵的失败。在分类账文件中跟踪进度，而不仅仅是在待办中。

- 在 skill 启动时，检查分类账：
  `cat "$(git rev-parse --show-toplevel)/.superpowers/sdd/progress.md"`。那里列为已完成的任务是 DONE——不要重新派发它们；从第一个未标记为完成的任务恢复。
- 当任务的审查返回干净时，在同一消息中向分类账追加一行，与你的其他簿记一起：
  `Task N: complete (commits <base7>..<head7>, review clean)`。
- 分类账是你的恢复地图：它命名的提交即使你的上下文不再记得创建它们也存在于 git 中。压缩后，信任分类账和 `git log` 而不是你自己的回忆。
- `git clean -fdx` 会销毁分类账（它是 git-ignored 的临时文件）；如果发生这种情况，从 `git log` 恢复。

## 优势

**vs. 手动执行：**
- 子代理自然遵循 TDD
- 每个任务有新鲜上下文（无混淆）
- 并行安全（子代理不干扰）
- 子代理可以提问（在开始前和工作中）

**vs. Executing Plans：**
- 同一会话（无交接）
- 连续进度（无等待）
- 审查检查点自动

**效率提升：**
- 控制器精确构造需要的上下文；大块工件作为文件移动，而不是粘贴的文本
- 子代理预先获得完整信息
- 问题在工作开始前浮出（而不是之后）

**质量关卡：**
- 自审在交接之前捕获问题
- 任务审查携带两个裁决：规格合规和代码质量
- 审查循环确保修复实际有效
- 规格合规防止过度/不足构建
- 代码质量确保实现构建良好

**成本：**
- 更多子代理调用（每个任务的实现者 + 审查员）
- 控制器做更多准备工作（预先提取所有任务）
- 审查循环增加迭代
- 但早期捕获问题（比稍后调试更便宜）

## 红旗

**永远不要：**
- 在没有明确用户同意的情况下在 main/master 分支上开始实现
- 跳过任务审查，或接受缺少任一裁决的报告（规格合规和任务质量都是必需的）
- 用未修复的问题继续
- 并行派发多个实现子代理（冲突）
- 让子代理读取整个计划文件（将它的任务简报交给它——`scripts/task-brief`——代替）
- 跳过场景设置上下文（子代理需要理解任务适合哪里）
- 忽略子代理问题（在让它们继续之前回答）
- 在规格合规上接受"足够接近"（审查员发现规格问题 = 未完成）
- 跳过审查循环（审查员发现问题 = 实现者修复 = 再次审查）
- 让实现者自审替代实际审查（两者都需要）
- 告诉审查员不要标记什么，或在派发提示中预评发现的严重性（"最多视为 Minor"）——计划的示例代码是起点，而不是其弱点被选择的证据
- 在没有 diff 文件的情况下派发任务审查员——先生成它（`scripts/review-package BASE HEAD`）并在提示中命名打印的路径
- 当审查有未解决的 Critical/Important 问题时进入下一个任务
- 在进度分类账已将任务标记为完成后重新派发任务——在任何压缩或恢复后检查分类账（和 `git log`）

**如果子代理提问：**
- 清晰完整地回答
- 如果需要，提供额外的上下文
- 不要催促它们进入实现

**如果审查员发现问题：**
- 实现者（相同子代理）修复它们
- 审查员再次审查
- 重复直到批准
- 不要跳过重新审查

**如果子代理任务失败：**
- 用具体指令派发修复子代理
- 不要尝试手动修复（上下文污染）

## 集成

**必需的工作流 skill：**
- **superpowers:using-git-worktrees** - 确保隔离工作区（创建一个或验证已存在）
- **superpowers:writing-plans** - 创建这个 skill 所执行的计划
- **superpowers:requesting-code-review** - 最终全分支审查的代码审查模板
- **superpowers:finishing-a-development-branch** - 所有任务完成后完成开发

**子代理应使用：**
- **superpowers:test-driven-development** - 子代理为每个任务遵循 TDD

**替代工作流：**
- **superpowers:executing-plans** - 用于并行会话而不是同一会话执行

## 附录 A：实现者子代理提示词模板

> 翻译自 `skills/subagent-driven-development/implementer-prompt.md`

在派发实现者子代理时使用此模板。

```
Subagent (general-purpose):
  description: "实现任务 N：[任务名称]"
  model: [MODEL — 必须：根据 SKILL.md 模型选择为每个角色选择；省略的模型会静默继承会话最贵的模型]
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    先读你的任务简报：[BRIEF_FILE]
    它包含计划中任务的完整文本。

    ## 上下文

    [场景设置：它适合哪里，依赖关系，架构上下文]

    ## 在你开始之前

    如果你有以下问题：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖关系或假设
    - 任务描述中任何不清楚的地方

    **现在就问它们。** 在开始工作之前提出任何疑虑。

    ## 你的工作

    一旦你清楚了需求：
    1. 精确实现任务指定的内容
    2. 编写测试（如果任务说要遵循 TDD）
    3. 验证实现工作
    4. 提交你的工作
    5. 自审（见下文）
    6. 回报

    从以下目录工作：[directory]

    **当你工作时：** 如果你遇到意外或不清楚的事情，**提问**。
    暂停并澄清总是可以的。不要猜测或做假设。

    迭代时，运行你正在变更的聚焦测试；在提交之前运行整个套件一次，而不是每次编辑后。

    ## 代码组织

    你对能一次性放入上下文的代码推理得更好，当文件聚焦时你的编辑也更可靠。记住这一点：
    - 遵循计划中定义的文件结构
    - 每个文件应有一个清晰的职责和定义良好的接口
    - 如果你正在创建的文件增长超出计划的意图，停下来并将其报告为 DONE_WITH_CONCERNS——不要在没有计划指导的情况下自行拆分文件
    - 如果你正在修改的现有文件已经很大或混乱，小心工作并在报告中将其记录为疑虑
    - 在现有代码库中，遵循既定模式。改进你正在接触的代码，就像好开发者会做的那样，但不要重构任务之外的内容。

    ## 当你力不从心时

    停下来并说"这对我来说太难了"总是可以的。糟糕的工作比没有工作更糟。你不会因为升级而受罚。

    **遇到以下情况时 STOP 并升级：**
    - 任务需要具有多种有效方法的架构决策
    - 你需要理解所提供的之外并且无法找到清晰度的代码
    - 你对你的方法是否正确感到不确定
    - 任务涉及计划未预期的现有代码重构
    - 你一直在读一个又一个文件，试图理解系统而没有进展

    **如何升级：** 回报状态为 BLOCKED 或 NEEDS_CONTEXT。具体描述你卡在哪里、你尝试了什么，以及你需要什么样的帮助。控制器可以提供更多上下文、用更强的模型重新派发，或将任务分解为更小的片。

    ## 回报之前：自审

    用新的眼光审查你的工作。问自己：

    **完整性：**
    - 我是否完全实现了规格中的所有内容？
    - 我是否漏掉了任何需求？
    - 是否有我没处理的边缘情况？

    **质量：**
    - 这是我最好的工作吗？
    - 名称是否清晰准确（匹配它们做什么，而不是它们如何工作）？
    - 代码是否干净且可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了被请求的内容？
    - 我是否遵循了代码库中的现有模式？

    **测试：**
    - 测试是否实际验证行为（而不只是模拟行为）？
    - 如果需要，我是否遵循了 TDD？
    - 测试是否全面？
    - 测试输出是否干净（没有杂散警告或噪音）？

    如果在自审期间发现问题，在报告之前现在就修复它们。

    ## 审查发现之后

    如果审查员发现问题并且你修复了它们，重新运行覆盖修订后代码的测试，并将结果附加到你的报告文件中。审查员不会为你重新运行测试——你的报告是测试证据。

    ## 报告格式

    将你的完整报告写入 [REPORT_FILE]：
    - 你实现了什么（或如果受阻，你尝试了什么）
    - 你测试了什么和测试结果
    - **TDD 证据**（如果此任务需要 TDD）：
      - RED：运行的命令、实现之前的相关失败输出，以及为什么预期会失败
      - GREEN：运行的命令和实现之后的相关通过输出
    - 变更的文件
    - 自审发现（如果有）
    - 任何问题或疑虑

    然后只回报以下内容（15 行以内——细节在报告文件中）：
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 创建的提交（短 SHA + 主题）
    - 一行测试摘要（例如"14/14 通过，输出干净"）
    - 你的疑虑（如果有）
    - 报告文件路径

    如果 BLOCKED 或 NEEDS_CONTEXT，将具体情况放入最终消息本身——控制器直接对其采取行动。

    如果你完成了工作但对正确性有疑虑，使用 DONE_WITH_CONCERNS。
    如果你无法完成任务，使用 BLOCKED。如果你需要未提供的信息，使用 NEEDS_CONTEXT。永远不要静默产生你不确定的工作。
```

## 附录 B：任务审查员提示词模板

> 翻译自 `skills/subagent-driven-development/task-reviewer-prompt.md`

在派发任务审查员子代理时使用此模板。审查员读取任务的一次性 diff 并返回两个裁决：规格合规和代码质量。

**目的：** 验证一个任务的实现是否匹配其需求（不多不少）并且构建良好（干净、经过测试、可维护）

```
Subagent (general-purpose):
  description: "审查任务 N（规格 + 质量）"
  model: [MODEL — 必须：根据 SKILL.md 模型选择为每个角色选择；省略的模型会静默继承会话最贵的模型]
  prompt: |
    你正在审查一个任务的实现：首先是否匹配其需求，然后是否构建良好。这是一个有任务范围的关卡，而不是合并审查——所有任务完成后会单独进行广泛的全分支审查。

    ## 被请求什么

    读取任务简报：[BRIEF_FILE]

    绑定此任务的规格/设计中的全局约束：
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称他们构建了什么

    读取实现者的报告：[REPORT_FILE]

    ## 正在审查的 Diff

    **Base：** [BASE_SHA]
    **Head：** [HEAD_SHA]
    **Diff 文件：** [DIFF_FILE]

    一次性读取 diff 文件——它包含提交列表、统计摘要和带周围上下文的完整 diff，它是你对变更的视图。diff 的上下文行就是变更的文件：除非你必须判断的块在函数中间被截断，否则不要单独读取变更的文件——并在你的报告中说明。不要重新运行 git 命令。
    如果 diff 文件缺失，自己获取 diff：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬取更广泛的代码库。只在你能说出具体风险的情况下才检查 diff 之外的代码——每个命名的风险进行一次聚焦检查，并在你的报告中命名风险和你检查的内容。跨切割变更是合法的命名风险：如果 diff 变更锁排序、函数或 API 契约，或共享可变状态，检查调用点是正确的方法。

    你对此 checkout 的审查是只读的。不要以任何方式变更工作树、索引、HEAD 或分支状态。

    ## 不要信任报告

    将实现者的报告视为关于代码的不经验证的主张。它可能不完整、不准确或乐观。根据 diff 验证主张。报告中的设计理由也是主张："按 YAGNI 保留"，"故意保持简单"，或任何其他理由都是实现者给自己评分。根据优点判断代码——陈述的理由永远不会降低发现的严重性。

    ## 测试

    实现者已经运行了测试，并使用完全针对此代码的 TDD 证据报告了结果。不要重新运行套件来确认他们的报告。只在读取代码引发了具体疑虑时才运行测试——并且是聚焦测试，绝不是包范围的套件、竞态检测器运行或重复/高计数循环。如果你不能在这个环境中运行命令，命名你会运行的测试。

    实现者报告的测试输出中的警告或其他噪音是发现——测试输出应该是干净的。

    ## 第 1 部分：规格合规

    将 diff 与"被请求什么"进行比较：

    - **缺失：** 他们跳过、漏掉或声称而没有实现的需求
    - **额外：** 未请求的功能、过度工程、不需要的"好东西"
    - **误解：** 以错误方式构建的正确功能，解决了错误的问题

    如果某个需求无法仅从此 diff 验证（它存在于未更改的代码中或跨任务），请将其报告为 ⚠️ 项，而不是扩大你的搜索。

    ## 第 2 部分：代码质量

    **代码质量：**
    - 关注点清晰分离？
    - 正确的错误处理？
    - DRY 而没有过早抽象？
    - 边缘情况已处理？

    **测试：**
    - 新的和变更的测试是否验证真实行为，而不是模拟？
    - 任务的边缘情况是否已覆盖？

    **结构：**
    - 每个文件是否有一个清晰的职责和定义良好的接口？
    - 单元是否分解得可以独立理解和测试？
    - 实现是否遵循计划中的文件结构？
    - 此变更是否创建了已经是大型的新文件，或显著增长了现有文件？（不要标记预先存在的文件大小——专注于此变更贡献了什么。）

    你的报告应指向证据：每个发现的文件：行引用，以及你可以否则用空"是"回答的任何检查。一份紧凑的报告，引用行，给控制器它需要的一切。

    你的最终消息就是报告本身：直接以规格合规裁决开始。每一行都是裁决、带有文件：行的发现，或你运行的检查——没有前言、没有过程叙述、没有结束摘要。

    ## 校准

    按实际严重性对问题进行分类。不是所有事情都是 Critical。
    Important 意味着此任务在修复之前不能被信任：不正确或脆弱的行为、漏掉的需求，或你会在合并时阻止的可维护性损害——逻辑块的逐字重复、被吞没的错误、不断言任何内容的测试。"覆盖可以更广"和润色建议是 Minor。
    如果计划或简报明确要求此审查标准视为缺陷的内容（不断言任何内容的测试、逻辑块的逐字重复），那是一个发现——将其报告为 Important，标记为 plan-mandated。计划的作者不会给自己的工作评分；人类决定。
    在你列出问题之前，承认做得好的地方——准确的赞扬有助于实现者信任其余的反馈。

    ## 输出格式

    ### 规格合规

    - ✅ 规格合规 | ❌ 发现问题：[缺失/额外/误解，附文件：行引用]
    - ⚠️ 无法从 diff 验证：[你无法仅从 diff 验证的需求，以及控制器应检查的内容]——将 ⚠️ 与 ✅/❌ 裁决一起报告你可以验证的每个项

    ### 优点
    [什么地方做得好？要具体。]

    ### 问题

    #### Critical（必须修复）
    #### Important（应该修复）
    #### Minor（可以更好）

    对于每个问题：文件：行、什么问题、为什么它重要、如何修复（如果不明显）。

    ### 评估

    **任务质量：** [批准 | 需要修复]

    **理由：** [1-2 句技术评估]
```

**占位符：**
- `[MODEL]` — 必须：根据 SKILL.md 模型选择选择审查员模型
- `[BRIEF_FILE]` — 必须：任务简报文件（`scripts/task-brief PLAN N` 打印路径；实现者从中工作的相同文件）
- `[GLOBAL_CONSTRAINTS]` — 绑定此任务的来自计划全局约束节或规格的精确要求：精确值、格式，以及组件之间的陈述关系（不是过程规则——它们已经在这个模板中）
- `[REPORT_FILE]` — 必须：实现者将其详细报告写入的文件
- `[BASE_SHA]` — 此任务之前的提交
- `[HEAD_SHA]` — 当前提交
- `[DIFF_FILE]` — 必须：控制器将审查包写入的路径（`scripts/review-package BASE HEAD` 打印它写入的唯一路径；包永远不会进入控制器的上下文）

**审查员返回：** 规格合规裁决（✅/❌/⚠️）、优点、问题（Critical/Important/Minor）、任务质量裁决

修复派发可以同时解决规格缺口和质量发现；修复后的重新审查覆盖两个裁决。
