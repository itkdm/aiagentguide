# 什么是 AI Agent？它和普通 LLM 应用到底有什么区别？

## 1. 面试官：先说说你理解的 AI Agent 是什么？

**面试者：** 我现在更愿意从“它怎么把事情做完”这个角度理解 Agent。比如给它一个目标以后，它不只是返回一段话，还能自己判断下一步，去查资料、调用接口或者操作文件；拿到结果以后，如果发现还没解决，就接着往下做。

拿代码分析来说，普通模型可能根据已经放进上下文的代码直接给意见。Agent 则可能先找入口文件，再搜索调用关系，运行测试，看到报错后继续定位。具体能做到哪一步，要看工具和运行时怎么设计，但它至少是在围绕一个任务持续推进，而不只是完成一次文本生成。

**补充说明：** 这段回答先讲行为，没有急着报组件名，这更接近真实面试。正式一点说，Agent 是让模型参与任务执行和下一步决策的软件系统。

模型、工具、状态和运行时都是实现 Agent 的常见部分，但不是固定清单。真正需要抓住的是：系统有没有目标，模型有没有一定的决策权，行动结果有没有机会影响后续步骤。

## 2. 面试官：Agent 是最近大模型出来以后才出现的概念吗？

**面试者：** 不是。这个词在大模型之前就有了，只是以前说 Agent，背后可能是规则、搜索或者规划算法。现在大家讨论得比较多的，是把大模型放到这个系统里，让它负责理解目标和做一部分决策。

大模型确实改变了构建方式。以前很多输入变化都要靠规则覆盖，现在模型可以先理解自然语言、文档和代码，再在限定范围内选择下一步。但一个固定流程里的分类器、摘要器，即使用了大模型，也还是普通的 LLM 应用，不一定就是 Agent。

**补充说明：** 这里把“Agent 这个系统概念”和“基于大模型实现的 Agent”分开就够了，不需要把回答讲成一段 AI 发展史。面试官更关心的是：不要因为系统用了 LLM，就把它直接叫作 Agent。

## 3. 面试官：既然 Agent 这个概念早就有了，为什么这几年突然爆火？

**面试者：** 我觉得不能只归结为一个原因。以前也有人做 Agent，但很多地方依赖规则，任务一复杂、输入一变化，维护成本就会上去。现在的大模型能理解比较开放的目标，也能处理文档、代码和对话，这让很多原来写不完规则的地方有了另一种实现方式。

另一个变化是工具调用。模型不只输出文字，还可以按约定选择搜索、数据库或业务 API，并把返回结果接着用于下一步判断。代码修复、资料研究、工单处理这些任务，本来就经常遇到信息不完整和路径变化，所以这种能力比较有用。

当然，能用 Agent 不代表就应该用 Agent。流程稳定、风险高、必须容易审计的业务，确定性的代码或 Workflow 可能更合适。

**补充说明：** 这道题回答“为什么现在更容易做”，不是回答“Agent 和普通 LLM 应用有什么区别”。把模型能力、工具接入和真实任务类型连起来，回答就不会停在“因为大模型变强了”。

## 4. 面试官：你刚才提到现在的 Agent 很大程度上建立在大模型之上，那它和普通的大模型应用最核心的区别是什么？

**面试者：** 我会先看控制权在谁手里。普通 LLM 应用里，代码通常已经把主要步骤定好了，模型负责分类、抽取、总结或者生成内容；下一步做什么，还是程序说了算。

Agent 会把一部分执行权交给模型。系统给它目标、当前状态、可用工具和限制条件，模型根据这些信息决定下一步；行动结束后，结果还会回到系统里，影响后面的判断。所以它更像是：

```text
普通 LLM 应用：输入 → 调用模型 → 输出

Agent：目标 → 决定下一步 → 执行动作 → 获得反馈
      → 再决定下一步 → 完成或停止
```

这不是绝对的二分。一个 Workflow 里也可以放一个负责动态路由的模型节点，这时不能简单说整个系统就是完全自治的 Agent。关键还是看模型拿到了多少工作流控制权，以及它能不能根据结果继续调整。

**补充说明：** 这道题的区分点不是“有没有大模型”，而是“模型有没有参与控制流程”。普通应用也可以由代码调用搜索或数据库，因此只说“Agent 能调用工具”不够。

如果模型只负责把输入变成输出，它更像 LLM 能力节点；如果模型参与决定任务如何继续执行，并且执行结果会影响后续步骤，才开始接近 Agent。

## 5. 面试官：如果一个 Chatbot 也能理解用户意图、连续对话，它为什么不一定算 Agent？

**面试者：** 因为理解用户和记住聊天记录，解决的是对话问题，不一定代表系统在执行任务。

一个 Chatbot 可以保存历史消息，让用户连续问几轮；也可以根据意图匹配不同的回复。这些功能都很有用，但如果每一轮仍然是用户输入、模型回答，系统没有主动去完成一件事情，也没有根据外部执行结果调整后续步骤，那它更适合叫对话式 LLM 应用。

比如一个机器人能够解释退款政策，它可能很会聊天，但主要还是在回答问题。另一个系统收到“帮我处理这笔退款”以后，会查询订单、检查条件、要求补材料、提交申请，失败时重试或转人工，这个系统就更接近 Agent。

这里的“主动”不是说它必须在用户不说话时自己发消息，而是说在一次任务执行过程中，它可以根据目标和当前结果决定下一步，而不是每一步都等程序提前写好。

**补充说明：** “对话”和“任务执行”是这里的分界。Chatbot 本身并不是低级系统，很多场景只需要稳定回答问题，没有必要为了贴上 Agent 标签增加动态执行能力。

判断一个 Chatbot 是否接近 Agent，可以继续追问三点：有没有明确任务目标？能不能采取外部行动？能不能根据行动结果继续调整？连续对话本身不是充分条件。

## 6. 面试官：如果再给这个 Chatbot 加上工具调用能力呢？你会怎么判断？

**面试者：** 这个时候我还是不会直接说它就是 Agent。我会看工具是谁决定调用的，以及工具返回以后有没有改变后面的流程。

比如流程写成“用户提问、固定调用搜索、把结果交给模型总结、返回答案”，这里虽然有模型和工具，但搜索一定发生，顺序也固定，模型没有根据中间结果决定要不要继续查。它更像是 Workflow 里加了一个工具节点。

如果系统给模型搜索、代码读取和测试工具，模型先决定查哪些文件，发现信息不够时继续搜索，测试失败后根据报错调整方案，最后在达到停止条件后输出结果，这才是更典型的 Agent Loop。

如果只是代码固定调用搜索，再让模型总结，工具只是普通流程中的一个节点。要是模型能根据当前结果决定继续查、换工具，或者进入下一步，才更像 Agent。多步执行、异常处理和结束条件也要一起看。

**补充说明：** Tool Calling 是一种能力接口，Agent 是一种系统形态。工具是 Agent 常用的手段，但不是充分条件。

这也是为什么“LLM + Tools”这个公式不够准确。它能帮助理解 Agent 的组成，却不能单独判断一个系统是不是 Agent。

## 7. 面试官：那 Planning、Memory、Tools 这些能力，是不是一个 Agent 都必须具备？

**面试者：** 我不会拿这三个词做硬性检查。任务简单的时候，可能一个工具加几轮模型调用就够了；任务变复杂以后，才需要更明确的计划、状态保存和长期记忆。

一个简单 Agent 可能只需要根据用户目标选择一个工具，拿到结果后返回，不一定需要显式列出完整计划，也不一定需要跨会话记忆。反过来，如果是分析大型代码库的 Agent，任务步骤比较多，就可能需要拆解任务、记录已经查过的文件、保留测试结果，并且在失败后重新调整方案。

Tools 主要解决“系统怎么和外部环境交互”；Planning 解决“复杂目标怎么安排步骤”；Memory 解决“过去的状态和结果怎么保留下来”。但它们的实现不固定：计划可以显式输出，也可以只在每一轮决策里隐式形成；Memory 也不一定等于向量数据库，当前任务状态、历史消息、数据库记录和文件都可能承担记忆作用。

所以我更关注它实际怎么工作：模型有没有参与决策，系统能不能采取行动，拿到结果以后能不能接着推进。

**补充说明：** 这里最容易掉进“组件清单”的坑。Planning、Memory、Tools 解决的问题不同，但没有一个统一清单能覆盖所有 Agent。

Planning 可以是显式计划，也可以只是每轮调用前的一次决策；Memory 也不等于向量数据库，任务状态、消息、文件或业务记录都可能承担记忆作用。组件是实现手段，任务行为才是判断依据。

## 8. 面试官：既然不能简单看有没有某个组件，那你通常会从哪些维度判断一个系统的 Agentic 程度？

**面试者：** 如果是我来判断，我会先看一件事：这个系统到底把多少执行权交给了模型。它只是生成一段内容，还是要自己决定下一步、做完几件事？

如果路径完全由代码写死，模型更像其中一个能力节点；如果模型能根据当前状态选择工具和路径，系统的自主决策程度就更高。还要看它和外部环境交互以后，结果是否真的会影响下一步，而不是只拿来拼最终答案。

再往后看，就是任务状态、失败处理、最大步数、权限限制和人工接管这些东西。系统越能在边界内持续调整，越接近 Agent；但这不是一个有统一分数的官方指标。

我最后会回到一个实际判断：模型是否在目标和边界内拥有一定的下一步决策权，能不能通过行动获得反馈，再调整执行。如果主要流程还是代码控制，就没必要为了概念包装把它叫成完整 Agent。

**补充说明：** “Agentic 程度”可以理解成“系统的自主决策程度”，不是一个有统一分数的官方指标。面试时先说这个核心判断，再根据项目补充决策权、外部交互、反馈闭环和边界控制，比一次背出一长串维度更自然。

## 9. 面试官：Agent 的自主性越强，是不是就说明这个系统设计得越好？

**面试者：** 不一定。我做设计时不会先追求“让模型自己做更多”，而是先看哪些环节确实需要它来判断。自主性提高以后，选错工具、重复执行、陷入循环和误操作的风险也会一起提高。

如果任务本身规则清楚、流程稳定，我会优先把它交给代码或 Workflow。模型更适合处理自然语言理解、非结构化信息和动态路径选择。涉及发消息、改生产数据、退款、权限变更这类动作，还要加参数校验、权限控制和人工确认。

比如报销系统可以让模型识别票据、补充信息、判断应该进入哪条审核路径，但金额校验、权限判断和最终付款不应该只靠模型自由决定。我的判断是，模型应该在真正需要灵活性的地方承担决策，确定性要求高的部分仍然由代码兜底。

**补充说明：** 这道题真正考的是工程取舍。自主性提高了处理不确定任务的能力，也会增加错误、成本、延迟和审计风险。

比较稳的判断是：**自主性应该匹配任务的不确定性、错误成本、审计要求和可验证性。能用确定性方案解决的问题，不需要为了 Agent 而 Agent 化。**

## 10. 面试官：最后如果让你用一句话概括 Agent 和普通 LLM 应用的本质区别，你会怎么回答？

**面试者：** 如果只用一句话，我会说：普通 LLM 应用主要负责生成回答，而 Agent 会利用模型和外部能力，围绕目标决定并执行下一步。

**补充说明：** 这句话短，但没有把 Agent 简化成“能调用工具”。真正要展开时，补上三个判断点就够了：谁控制流程、有没有外部行动、执行结果会不会影响后续决策。

## 这篇要记住什么

### 必须掌握

- Agent 的重点不是聊天，而是围绕目标持续推进任务。
- 判断 Agent 的关键，不是有没有某个组件，而是模型是否参与下一步决策，并根据环境反馈继续执行。
- Tool Calling 是能力接口，Agent 是系统形态；有工具不一定就是 Agent。
- 自主性不是越强越好，系统应该根据任务不确定性、风险和审计要求划分模型与代码的边界。

### 理解即可

- Agent 这个概念早于大模型，今天流行的是以大模型为核心的 Agent 系统。
- Planning、Memory、Tools 的实现形式很多，不同框架的抽象也不完全一样。
- Agentic 程度更适合看成连续谱，而不是简单的“是”或“不是”。

### 能不能自己讲出来？

如果有人问“Agent 和普通 LLM 应用最大的区别是什么”，不要只回答“Agent 可以调用工具”。更完整的回答应该包含三层：普通 LLM 应用通常由代码控制主要流程；Agent 会让模型参与下一步决策；执行结果还会回到系统中，影响后续行动。

能把这条因果关系讲清楚，比背下一句固定定义更重要。
