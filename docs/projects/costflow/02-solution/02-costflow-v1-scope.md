# 确定 CostFlow V1：第一版到底要做什么

上一篇我们分别看了 New API 和 Sub2API。

它们给了我们很多可以参考的思路：

```text
New API
→ 预扣
→ 调用模型
→ 根据真实 Usage 重新结算

Sub2API
→ 最低余额 + 并发控制
→ 调用模型
→ 根据真实 Usage 后扣费用
```

但参考到这里已经足够了。

CostFlow 不是 New API，也不是 Sub2API。

它们本身都是完整的 AI API Gateway，除了计费，还要解决渠道、API Token、模型转发、负载均衡、订阅、支付等很多问题。

CostFlow 当前没有必要把这些能力全部重新做一遍。

接下来应该重新回到我们的项目：

> **CostFlow 第一版真正要解决什么问题？**

这一篇先把产品范围确定下来。

暂时不讨论数据库怎么建，也不急着设计具体的 Service 和接口。

---

## 先回到我们现在的系统

RuoYi Vue Pro 已经给我们准备好了两块非常重要的能力。

第一块是用户。

现有系统已经有自己的：

```text
用户
租户
角色
权限
管理后台
```

因此 CostFlow 不需要重新创建一套用户体系。

第二块是模型。

前面我们已经跑通：

```text
API Key
    ↓
AI Model
    ↓
Spring AI
    ↓
Provider
```

模型怎么接入、API Key 怎么配置、聊天怎么调用，这些都已经存在。

所以 CostFlow 第一版真正需要补上的，是中间缺失的这一段：

```text
现有用户
    ↓
现有 AI 模型
    ↓
模型调用
    ↓
用了多少？
    ↓
值多少钱？
    ↓
这个用户还能不能继续用？
```

也就是：

```text
Usage
    ↓
Metering
    ↓
Pricing
    ↓
Billing
```

## CostFlow 第一版的整体结构

先不考虑具体类名和数据库表，可以先把 CostFlow 拆成几个产品能力。

```text
                    CostFlow

          ┌────────────┴────────────┐
          │                         │
      用户账户                   模型价格
      Account                    Pricing
          │                         │
          └────────────┬────────────┘
                       │
                       ▼
                  模型调用
                       │
                       ▼
                     Usage
                       │
                       ▼
                  Metering
                  用量标准化
                       │
                       ▼
                    Billing
                   费用计算
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
       账户余额                   资金流水
       Balance                    Ledger
          │
          └────────────┬────────────┘
                       ▼
                  查询与统计
```

另外还有一层会挡在模型调用之前：

```text
调用保护

├── 最低余额
└── 用户并发限制
```

这就是 CostFlow V1 最核心的产品结构。

## 用户额度就是钱

这里先确定一个非常重要的概念。

CostFlow 中的用户额度不是积分，也不是需要二次换算的虚拟 Quota。

它直接对应真实金额。

例如：

```text
小明

账户余额：
¥10.00
```

模型又有自己的真实价格：

```text
输入：
¥2 / 1M Tokens

输出：
¥8 / 1M Tokens
```

一次调用产生：

```text
Input  = 10000 Tokens
Output = 1000 Tokens
```

CostFlow 根据真实模型价格计算：

```text
Input Cost
+
Output Cost
=
本次消费
```

然后直接从用户余额中扣除对应金额。

所以在 CostFlow 中：

> **余额就是钱，Usage 决定这一次需要花多少钱。**

## 第一版不做充值和订阅

既然账户里面是真实金额，是不是马上就要接：

```text
支付宝
微信支付
Stripe
充值订单
套餐
订阅
```

完全没有必要。

第一版只需要：

```text
管理员
    ↓
找到用户
    ↓
给用户增加 ¥10
```

用户就可以开始使用。

例如公司内部部署 CostFlow：

```text
实习生小明
→ 管理员发放 ¥20 AI 使用额度

开发人员小红
→ 管理员发放 ¥100 AI 使用额度
```

这已经可以满足一个真实的内部使用场景。

管理员也可以增加余额、减少余额、查看余额和查看消费记录。

至于用户自己充值、套餐、订阅和支付渠道，全部留到以后。

我们没有必要为了完成第一版计费系统，先做一整套支付平台。

## 一次真实模型调用是最小计费单位

前面我们已经发现，一次聊天消息不能永远等于一次模型调用。

现在 Chat 里面看起来可能很简单：

```text
用户发送消息
    ↓
模型调用一次
    ↓
模型回答
```

但以后 Agent 很可能是：

```text
Agent Run
    │
    ├── LLM Call 1
    │
    ├── Tool
    │
    ├── LLM Call 2
    │
    └── LLM Call 3
```

真正产生模型费用的是每一次 LLM Call，而不是 Agent Run 本身。

所以 CostFlow 从第一版开始就应该坚持：

> **一次真实 Model Call，是最小的模型计费事实。**

第一版先把它接到 AI Chat。

以后再接 Write、MindMap、Workflow、Agent 时，不需要重新改变这个基本模型。

## Usage 不能只记录一个 Total Tokens

模型价格已经越来越复杂。

最简单的模型可能只有：

```text
Input Tokens
Output Tokens
```

但真实 Provider 还可能返回：

```text
Cache Read
Cache Write
Reasoning Tokens
5 分钟缓存创建
1 小时缓存创建
```

而且这些 Usage 的价格可能完全不同。

因此 CostFlow 不能最终只得到：

```text
Total Tokens = 12345
```

而应该能够把一次模型调用拆成不同用量：

```text
INPUT
OUTPUT
CACHE_READ
CACHE_WRITE
REASONING
...
```

例如：

```text
INPUT        4000
CACHE_READ   6000
OUTPUT        700
REASONING     300
```

后面的 Pricing 才能针对每一种用量分别计算费用。

### Spring AI 能提供多少，我们就先用多少

当前项目使用 Spring AI。

它已经能够统一提供最基础的 Prompt Tokens、Completion Tokens、Total Tokens，同时还保留 Provider 自己的原始 Usage。

但不同 Provider 返回的数据并不完全一样，当前项目使用的 Spring AI 版本也没有把所有 Cache、Reasoning 等字段都统一出来。

所以 CostFlow 第一版需要增加一层自己的 Usage 处理：

```text
Spring AI Usage
        ↓
Provider Usage
        ↓
CostFlow 统一 Usage
```

原则很简单：

```text
Spring AI 已经提供
→ 直接使用

Spring AI Provider 专属对象能够提供
→ 使用专属数据

nativeUsage 中还能取得
→ 继续解析

都没有可靠数据
→ 不凭空估算真实费用
```

因为 CostFlow 最终影响的不是一个统计图表，而是真实用户余额。

如果一次调用连可靠的 Token Usage 都拿不到，那么宁可记录这次异常调用，也不要随便估算一个数字然后直接扣用户的钱。

### 原始 Usage 和计费用量都要保留

不同 Provider 对 Usage 字段的语义可能不同。

例如某个平台返回：

```text
Prompt Tokens = 10000
Cached Tokens = 6000
```

其中 Cached Tokens 可能已经包含在 Prompt Tokens 中。

那么真正参与普通 Input 价格计算的可能应该是：

```text
10000 - 6000
=
4000
```

最终 CostFlow 的计费用量是：

```text
INPUT       4000
CACHE_READ  6000
```

而另外一个 Provider 可能从一开始就把普通输入和缓存输入分开返回。

所以我们需要区分：

```text
Provider 原始 Usage
```

和：

```text
CostFlow 标准化后的 Usage
```

可以把它理解成：

```text
Raw Usage
    ↓
Usage Normalization
    ↓
Billable Usage
```

原始 Usage 用于对账、排查和重新核算；标准化 Usage 才真正进入 Pricing。

## 模型价格必须足够灵活

知道用了多少以后，就要解决第二个问题：

> 这些 Usage 值多少钱？

最简单的模型：

```text
INPUT
¥2 / 1M Tokens

OUTPUT
¥8 / 1M Tokens
```

很好处理。

但有些模型还会提供 Cache Read、Cache Write、Reasoning 等不同价格。

甚至同一个模型还可能按照输入长度分档。

例如：

```text
0 ~ 32K Tokens
→ 一套价格

32K ~ 128K Tokens
→ 另一套价格

128K 以上
→ 又一套价格
```

所以 CostFlow 第一版的 Pricing 不能只设计成：

```text
模型
├── inputPrice
└── outputPrice
```

然后以后每出现一种新价格就继续增加字段。

我们应该从产品层面支持：

```text
一个模型
    ↓
多个价格区间
    ↓
每个区间拥有多种 Usage Price
```

例如：

```text
0 ~ 32K

INPUT        ¥4 / 1M
OUTPUT       ¥16 / 1M
CACHE_READ   ¥0.8 / 1M
CACHE_WRITE  ¥5 / 1M
```

如果模型没有阶梯价格：

```text
0 ~ ∞
```

就是唯一的一档。

这样普通定价和阶梯定价可以使用同一套产品模型。

### 历史价格不能跟着现在一起变

假设今天：

```text
INPUT = ¥2 / 1M
OUTPUT = ¥8 / 1M
```

明天管理员修改成：

```text
INPUT = ¥3 / 1M
OUTPUT = ¥10 / 1M
```

那么昨天已经产生的消费不能发生变化。

所以一次模型调用结算后，除了记录 Usage，还需要留下当时使用的价格，也就是价格快照。

这样以后查询一条历史消费时，可以明确知道：

```text
用了多少
×
当时是什么价格
=
为什么最后扣了这些钱
```

这对计费系统很重要。

## 第一版怎么限制用户继续调用

有了用户余额，就必须解决：

> 用户钱不够的时候，什么时候拦住请求？

上一篇我们看到过两种方案。

### New API：预扣

```text
预估费用
    ↓
冻结余额
    ↓
调用模型
    ↓
真实 Usage
    ↓
重新结算
    ↓
多退少补
```

这种方案控制比较严格。

但第一版会引入预估、冻结、解冻、补扣、退款和异常恢复整套流程。

对于 CostFlow V1 来说太早了。

### V1 采用最低余额 + 并发限制

第一版我们先采用更简单的方式：

```text
用户发起请求
    ↓
检查并发
    ↓
检查最低余额
    ↓
允许调用模型
    ↓
获得真实 Usage
    ↓
计算真实费用
    ↓
扣除余额
```

例如系统要求：

```text
最低余额：¥0.10
```

那么：

```text
余额 ¥3
→ 可以调用

余额 ¥0.05
→ 拒绝新调用
```

同时再限制：

```text
一个用户最多同时执行 3 个请求
```

这样可以降低用户在余额检查通过以后瞬间发起大量并发请求造成的超额风险。

### 第一版允许有限透支

最低余额 + 并发控制并不是严格的资金预留。

例如：

```text
余额 ¥1
```

三个请求同时通过检查。

最终三个请求分别消费：

```text
¥0.4
¥0.4
¥0.4
```

最终真实成本就是：

```text
¥1.2
```

即使账户只有 ¥1，我们也不能把最后 ¥0.2 的真实模型成本抹掉。

因此第一版允许账户在极端情况下出现：

```text
-¥0.2
```

但之后余额低于最低余额，新的模型调用会立即被阻止。

换句话说：

> **V1 的最低余额和并发限制属于风险控制，不是严格的资金预留。**

以后如果需要做到绝对不能透支，再升级为预扣方案。

## P0、P1、P2 怎么划分

到这里，CostFlow 的产品范围已经比较清楚了。

接下来把功能分成三个优先级。

```text
P0
→ CostFlow V1 必须完成
→ 缺少这些能力，核心计费链路无法成立

P1
→ V1 跑通以后补齐
→ 主要提升覆盖范围、管理体验和运营能力

P2
→ 后续扩展
→ 更复杂的计费方式、支付商业化以及 Agent 场景
```

## P0：第一版必须完成

P0 最重要的目标不是功能数量，而是完整跑通：

```text
用户
→ 模型调用
→ Usage
→ Pricing
→ Cost
→ Balance
→ Ledger
```

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P0 | 用户计费账户 | 为现有系统用户建立 CostFlow 账户，用真实金额表示可以继续消费的余额。 |
| P0 | 管理员调整余额 | 管理员可以为用户增加或减少余额，第一版通过人工发放额度代替充值系统。 |
| P0 | 账户流水 | 每一次管理员调额和模型消费都形成可追溯记录，能够解释余额为什么发生变化。 |
| P0 | 最低余额限制 | 用户余额低于系统最低余额时，禁止继续发起新的计费模型请求。 |
| P0 | 用户并发限制 | 限制单个用户同时进行的模型请求数量，降低后扣模式下的超额消费风险。 |
| P0 | 有限透支处理 | 已经通过检查的请求按真实 Usage 正常结算，即使造成少量负余额；负余额后停止新的调用。 |
| P0 | 模型价格管理 | 在现有 AI Model 基础上维护 CostFlow 的计费价格，不重复建设模型接入能力。 |
| P0 | 多 Usage 类型价格 | 支持 Input、Output、Cache、Reasoning 等不同 Usage 使用不同价格。 |
| P0 | Token 阶梯价格 | 支持按照一次请求的输入 Token 数量选择不同价格区间。 |
| P0 | 默认价格回退 | 某些特殊 Usage 没有单独价格时，可以按照明确规则回退到普通 Input 或 Output 价格，避免意外按 0 元计算。 |
| P0 | 模型调用记录 | 每次真实模型调用形成独立记录，作为 Usage 和费用结算的最小业务事实。 |
| P0 | 原始 Usage 保存 | 保存 Spring AI 或 Provider 返回的原始 Usage，方便后续核账和排查。 |
| P0 | Usage 标准化 | 将不同模型平台的 Usage 转换成 CostFlow 统一的 Input、Output、Cache、Reasoning 等用量。 |
| P0 | Provider Usage 兼容 | Spring AI 统一字段不足时，继续读取 Provider 专属 Usage 或 nativeUsage，尽可能获得可靠的实际用量。 |
| P0 | Usage 缺失保护 | 如果无法获得可信的计费用量，记录异常调用，但不根据猜测值直接扣除用户真实余额。 |
| P0 | 费用计算 | 根据标准化 Usage 和当前模型价格计算一次模型调用产生的真实费用。 |
| P0 | 费用明细 | 能看到不同 Usage 分别产生多少费用，而不仅仅保存一个总金额。 |
| P0 | 价格快照 | 每次结算保存当时实际采用的价格，后续修改模型价格不会影响历史消费。 |
| P0 | 调用后结算 | 模型调用完成以后，根据 Provider 返回的实际 Usage 计算并扣除真实金额。 |
| P0 | 重复结算保护 | 同一次模型调用只能真正结算一次，避免异常流程造成重复扣费。 |
| P0 | 调用状态 | 区分成功、失败、取消等调用状态，为费用判断和问题排查提供依据。 |
| P0 | AI Chat 接入 | 第一版先完整覆盖当前已经跑通的 AI Chat，包括同步和流式调用。 |
| P0 | Usage 明细管理 | 管理员可以查询每次模型调用的用户、模型、Usage、价格、费用和状态。 |
| P0 | 用户账户管理 | 管理员能够查看用户余额、累计消费和账户流水。 |
| P0 | 模型消费查询 | 可以从模型维度查看调用次数、Token 用量和产生的费用。 |
| P0 | 租户隔离 | CostFlow 的账户、调用记录和费用继续遵循现有系统的租户边界。 |

完成这些功能以后，CostFlow V1 应该能够真正跑通下面这条链：

```text
管理员给小明 ¥10
        ↓
给 DeepSeek 配置价格
        ↓
小明发送 AI Chat
        ↓
检查余额与并发
        ↓
调用模型
        ↓
Spring AI / Provider 返回 Usage
        ↓
CostFlow 标准化 Usage
        ↓
匹配对应价格区间
        ↓
计算本次消费
        ↓
扣除小明余额
        ↓
生成账户流水
        ↓
后台可以查询完整消费记录
```

做到这里，CostFlow 第一版就已经成立了。

## P1：把系统变得更完整

P1 不改变核心计费模型。

主要是在 P0 已经可靠运行以后，扩大覆盖范围，并补齐管理和统计能力。

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P1 | 更多 AI 功能接入 | 将 AI Write、MindMap 等现有模型调用逐步接入 CostFlow，而不仅仅统计 Chat。 |
| P1 | 更多 Provider Usage 适配 | 针对不同模型平台补充更完整的 Cache、Reasoning 等 Usage 解析。 |
| P1 | 更多缓存 Usage 类型 | 支持 5 分钟缓存创建、1 小时缓存创建等更细的 Provider 用量。 |
| P1 | 用户余额查询 | 普通用户可以查看自己的当前余额。 |
| P1 | 用户消费记录 | 普通用户可以查看自己的模型调用和历史消费。 |
| P1 | 多维度消费统计 | 按时间、用户和模型统计调用次数、Token 和费用。 |
| P1 | CostFlow Dashboard | 展示今日调用、今日消费、主要模型、活跃用户等基础数据。 |
| P1 | 低余额提醒 | 余额接近最低限制时提前通知用户或管理员。 |
| P1 | 用户级最低余额 | 在系统默认规则之外，为特殊用户设置不同的最低余额限制。 |
| P1 | 用户并发配置 | 管理员可以针对不同用户调整最大并发数量。 |
| P1 | 模型价格历史 | 查看模型价格曾经发生过哪些调整，方便理解历史消费。 |
| P1 | Usage 异常监控 | 集中查看无法获得有效 Usage、无法正常计费等异常模型调用。 |
| P1 | 费用核算工具 | 根据保存的 Raw Usage 对异常历史调用进行人工核查和重新计算。 |
| P1 | 管理员操作备注 | 调整余额等人工操作时填写原因，方便后续审计。 |
| P1 | 数据导出 | 导出 Usage、费用和账户流水，用于进一步分析或核对。 |

P1 完成以后，CostFlow 会从：

```text
能够计费
```

进一步变成：


## 哪些东西第一版明确不做

有时候确定“不做什么”和确定“做什么”一样重要。

CostFlow V1 明确不会因为“计费系统以后可能需要”就提前实现：

```text
用户充值
支付渠道
订阅套餐
优惠券
发票
复杂计费表达式
多币种
Agent 完整成本
部门预算
```

这些能力以后都可以继续增加。

但第一版先解决最核心的问题：

> **一个真实用户调用一个真实模型以后，CostFlow 能不能准确知道用了多少、值多少钱，并正确影响这个用户的余额？**

如果这一条链都还没有跑稳，那么继续做订阅和支付没有意义。

## V1 的几个基本原则

### 1. 余额就是真实金额

不再增加一层积分或者 Quota 换算。

```text
¥10
```

就是用户当前还能消费的金额。

### 2. 一次 Model Call 是最小计费事实

Chat、Write、Agent 都只是业务来源。

真正参与 Usage 和费用计算的是每一次实际模型调用。

### 3. Usage 和 Pricing 分开

Usage 回答：

```text
用了多少？
```

Pricing 回答：

```text
这些用量多少钱？
```

两者不能混在一起。

### 4. 历史消费必须可以解释

一条已经结算的模型调用至少应该能够回答：

```text
谁调用的？
调用什么模型？
用了多少？
当时价格是多少？
每一部分花了多少钱？
最终扣了多少钱？
```

### 5. V1 采用后扣模式

第一版采用：

```text
最低余额
+
用户并发限制
+
实际 Usage 后扣
```

先把方案控制在可以可靠实现的范围内。

### 6. 尽量使用真实 Usage

Spring AI 能够提供的数据优先使用。

如果统一 Usage 不够，再读取 Provider 专属 Usage。

CostFlow 不会为了“有一个数字”而随意估算并扣真实余额。

## CostFlow V1 最终应该是什么样

假设系统里已经有：

```text
用户：小明
模型：deepseek-chat
```

管理员先给小明：

```text
余额：¥10
```

然后配置模型价格。

小明打开现有 AI Chat，发送：

```text
帮我解释一下 MCP 的工作原理
```

请求正常进入现有模型调用链。

CostFlow 在这条链路旁边完成：

```text
检查余额
    ↓
检查并发
    ↓
记录模型调用
    ↓
获得真实 Usage
    ↓
标准化 Usage
    ↓
匹配模型价格
    ↓
计算费用
    ↓
扣除余额
    ↓
产生流水
```

管理员随后可以在后台看到：

```text
用户：
小明

模型：
deepseek-chat

Input:
3250 Tokens

Output:
812 Tokens

本次费用：
¥0.00xxxx

调用状态：
成功

调用时间：
xxxx-xx-xx xx:xx:xx
```

用户账户同时变成：

```text
原余额
¥10

本次消费
-¥0.00xxxx

当前余额
¥9.99xxxx
```

这就是我们第一阶段真正要完成的 CostFlow。

不是一个 Token 统计页面，也不是一个支付平台，而是一条真正能够运行的：

```text
Usage
→ Metering
→ Pricing
→ Billing
→ Account
```

完整链路。
