# CostFlow - 面向 AI 应用的用量、成本与计费系统

CostFlow 是「项目实践」栏目的第一个项目。

我们把它放在第一个，并不是因为计费是最典型的 Agent 功能，而是因为它刚好处在两个方向的交界处：**往前是大家更熟悉的 Java 后端工程，往后又能自然延伸到 AI 应用和 Agent 的用量与成本管理。**

所以如果你的目标非常明确，就是马上学习 Agent 如何规划、调用工具、管理状态，可以直接等待后面更偏 Agent 的项目。

但如果你已经有一些 Java 后端基础，又准备继续往 AI 应用或 Agent 开发方向走，我会更推荐从 CostFlow 开始。

它比较“进可攻，退可守”。

往 AI 应用方向继续做，可以逐步接入模型调用、Token 消耗、工具执行、Agent 任务成本；如果以后仍然主要做 Java 后端，它本身又是一个涉及数据建模、事务、幂等、并发、统计和系统设计的完整后端项目。

进入 CostFlow - AI 应用计费系统

## CostFlow 到底是什么

CostFlow 并不是从一个空文件夹重新搭建的项目。

**我们会基于芋道现有的开源工程进行二次开发，在一个已经具备真实业务模块和工程约束的系统中，逐步增加用量、成本与计费能力。**

也就是说，我们首先面对的不是：

> 如果让我从零写一个计费系统，我想怎么设计？

而是：

> 在一个已经运行着大量业务模块的系统里，计费能力应该放在哪里？怎样接入现有架构？哪些东西应该复用，哪些能力应该独立出来？

这也是 CostFlow 真正开始的地方。

## 我们为什么选择芋道

芋道是一套面向企业应用开发的开源快速开发平台，目前同时提供 Spring Boot 多模块和 Spring Cloud 微服务版本，并配套 Vue 管理后台。

它已经拥有用户、权限、多租户、支付、商城、CRM、ERP、AI 大模型等大量模块，本身就是一个体量不小、模块边界比较完整的 Java 开源工程。

这对 CostFlow 很重要。

因为我们不需要花大量时间重复搭建登录、权限、基础设施和管理后台，而是可以直接把注意力放到真正需要研究的计费问题上。

同时，它又不会让开发变得过于简单。

当我们真的准备加入一个新的计费能力时，仍然需要考虑已有模块怎样组织、数据怎样关联、接口怎样暴露、权限怎样处理，以及新的设计是否会影响现有系统。

换句话说，**我们不是只借芋道的技术栈，而是借它现有的工程复杂度来完成一次真正的二次开发。**

## 我们准备开发什么

CostFlow 最终要解决的核心问题，可以先用一句话概括：

> **把系统中发生的资源使用记录下来，并经过计量和定价，最终形成可以查询、统计和核对的费用数据。**

例如未来系统里可能出现：

- API 被调用了多少次
- 某项能力被使用了多少
- 一次任务实际消耗了多少资源
- 某种资源按照什么规则计价
- 一个用户在一段时间里产生了多少费用

到了 AI 场景以后，还可以继续出现：

- 模型调用次数
- Input / Output Token 消耗
- 不同模型产生的成本
- Tool 调用产生的第三方费用
- 一次 Agent 任务的总体成本

但这些不会在第一版全部做进去。

CostFlow 会先从芋道当前工程能够真正使用的通用计费能力开始，把最核心的链路建立起来，再随着项目继续演进扩展新的场景。

## 核心链路

目前整个项目最核心的一条链路可以先理解成：

**Usage → Metering → Pricing → Billing**

### Usage

先把一次真实发生的资源消耗记录下来。

谁使用了什么、用了多少、什么时候发生，以及这条数据后续应该怎样被识别，都从这里开始。

### Metering

Usage 是原始用量，Metering 负责进一步计量和聚合。

有的资源按照次数统计，有的按照数量统计，也可能需要按照时间窗口进行累计。

### Pricing

知道用了多少以后，还需要解决：

**这些用量应该按照什么规则计算价格？**

不同资源、不同规格甚至不同时间，都可能对应不同的价格规则。

### Billing

最后再把前面的用量和价格连接起来，形成真正能够查询和核对的费用结果。

随着项目推进，我们还会继续遇到重复上报、并发、事务一致性、异常恢复、规则变化、历史数据和统计查询等问题。

## 和芋道现有系统怎么结合

CostFlow 不会完全独立于芋道另起一套用户、权限和业务体系。

我们会先理解芋道现有的模块结构和基础能力，再决定计费模块应该怎样融入其中。

比如：

- 哪些现有用户或业务主体会产生 Usage
- 计费相关权限应该怎样接入现有权限体系
- 管理端需要提供哪些配置和查询能力
- 计费模块和其他业务模块之间应该通过什么边界交互
- 哪些能力应该放在模块内部，哪些应该设计成可以被其他模块调用的公共接口

这些问题会随着真正进入源码以后逐步确定。

第一阶段不会先凭空设计一个非常庞大的架构，而是先看现有项目，再做设计。

## 会用到哪些技术

CostFlow 会沿着芋道现有的 Java / Vue 工程体系继续开发。

整个过程中会逐渐涉及：

- Java 与 Spring Boot
- MyBatis Plus 与关系型数据库
- Redis
- Spring Security 与权限体系
- REST API 设计
- Vue 管理端
- 数据库与领域模型设计
- 事务与数据一致性
- 幂等与并发处理
- 单元测试与集成测试
- 日志与可观测性
- Git、Issue、PR 和开源协作

如果后续项目真正发展到需要消息队列、异步计费或者更加复杂的架构，再根据实际需求继续引入相应能力。

技术不是一次性堆上去的，而是跟着问题出现。

## 项目难度怎么样

**整体难度：中等起步，后期逐渐提高。**

如果已经做过普通的 Spring Boot CRUD 项目，前期应该能够比较顺利地进入。

真正开始拉开难度的地方不会是写 Controller 或 Service，而是后面这些问题：

- 数据模型到底应该怎样拆
- Usage 怎样保证不会重复
- 并发情况下怎样保证计费正确
- Pricing 发生变化以后历史费用怎么办
- 模块之间怎样避免过度耦合
- 新的计费类型怎样低成本接入
- 出现错误以后怎样追踪和修复

所以这个项目也比较适合作为从“会写业务功能”继续往“会做工程设计”过渡的项目。

## 你最终会得到什么

跟完整个项目以后，希望你得到的不只是一个计费模块。

更重要的是完整经历一次：

**阅读已有项目 → 理解需求 → 确定边界 → 设计方案 → 修改真实工程 → 测试验证 → 继续迭代**

的开发过程。

CostFlow 也会随着实际需求继续发展。

前期先解决通用的 Usage、Metering、Pricing 和 Billing，后续再逐渐探索模型调用、Agent 执行和 AI 应用成本管理。

最终它到底会发展到哪里，我们不提前把答案写死。

先从当前真实存在的问题开始。
